# 产品功能清单与云端设计提示词

> 状态：设计输入 · 2026-08-15  
> 本文件两件事：① 产品经理视角的功能全景（含文档 Git、文件变更进浏览器）；② 给云端 Agent 的提示词——**只出产品设计稿，禁止写代码**。

配套约束：[09-云端迭代入口.md](./09-云端迭代入口.md)、[00](./00-产品重定位.md)、[07](./07-客户端架构.md)。技术选型已拍板，设计稿不要重开 Tauri/Python/Casbin 之争。

## A. 产品要帮谁完成什么

**产品经理 / 产品设计**（主用户）  
技术人员把环境配好之后：把「去翻代码、问能不能做、补进 PRD」交给 AI；人负责判断、改文档、定稿。不看仓库、不配模型、不碰 MCP。

**架构师**（配环境的人）  
把一台机器变成可用环境：Claude、代码仓（只读）、**文档 Git 仓**、账号。自己也可以进工作台写技术方案。

核心转移：

```text
以前：PM 写草稿 → 拉研发看代码 → 改 PRD → 邮件/Wiki 里版本丢失
现在：架构师配好环境 → PM 对 AI 说需求 → AI 只读代码仓做调研 → 结论写进文档仓
      → 人在墨览里改 → 每次落盘进 Git（人写的和 AI 写的都能回看、对比、回退）
```

## B. 功能清单（按用户能感知的能力，不是按模块）

### B1. 环境（架构师，产品经理不碰）

- 安装并启动本机服务器；浏览器打开
- 第一个账号是架构师；创建产品经理账号
- 接上托管机 Claude（扫 `~/.claude`，MCP/skills 默认全开，可关）
- 挂 **代码根**（只读，可多个）：AI 调研用
- 挂 **文档根**：必须是（或初始化成）一个 **Git 仓库**；可关联 remote（GitHub/GitLab 等）
- 代码仓更新后，可让 AI「按最新代码再调研」（不必产品经理 pull）

### B2. 工作台（产品经理日常）

- 登录后只看到已有工程（不能改环境）
- 打开工程 = 文档仓里的交付物（PRD / 调研笔记 / 缺口 / 以后的 SR）
- 主区：**墨览**读和改 Markdown
- 侧区：**按阶段跟 AI 说话**（共创、拷问、可行性调研），不是空白 ChatGPT
- AI 用中文说人话（「正在搜设置页夜间模式相关实现」），不甩 tool JSON
- 长任务可离开：关浏览器再打开，按会话接着看；取消是明确按钮
- 可行性：AI **只读代码仓**，结论写进文档仓（如 `调研.md` / 写入 PRD 某节），不改业务代码
- 导入乱七八糟的 md / 粘贴，先保真再追问
- 缺口清单与文档章节对应，回答后写回文档

### B3. 文档版本（人写的、AI 写的，都进 Git）

文档根 = 该工程的 Git 真相源。Wiki、聊天记录、SQLite **都不是**版本库。

产品经理要能：

- 看到时间线：哪次是自己保存、哪次是 AI 写入、提交说明是什么
- 打开任意历史版本（墨览只读或恢复）
- 对比两个版本（尤其是「AI 刚改完」vs「我改之前」）
- 回退某一篇或整个仓到某次提交
- 区分「未提交的编辑」和「已进 Git」
- 可选：推到 remote，方便评审、备份、换机器

设计时必须拍板的交互（写入设计稿，不要留给开发猜）：

1. **何时 commit**：每次 Cmd+S？每次 AI 一轮结束？人点「保存版本」？AI 先放暂存区等人点「采纳并提交」？  
2. **AI 写入是否直接 commit**：静默提交 vs 待采纳（产品更倾向：AI 改磁盘可以，进 Git 主历史要可辨、可回退；是否要「采纳」请给方案）  
3. **提交说明**：自动生成（「AI：补验收标准」）+ 人可改  
4. **多人**：两个产品经理改同一篇 → 冲突怎么呈现（结合 etag + git）  
5. **分支**：第一版是否只用 `main` 直线历史，够不够

### B4. 磁盘一变，浏览器要知道

文档会从三条线变：① 我在墨览保存；② AI 写入；③ `git pull` / 另一人保存。

产品经理要能：

- 当前打开的篇若在别处被改：未编辑则自动换成新内容；有未保存修改则问「留我的 / 用新的 / 看差异」
- 侧栏文件树反映新增/删除/重命名（AI 新建了 `调研.md`）
- 长任务进行中，已写进磁盘的章节可以马上在墨览里看到
- 不要求 Google Docs 式逐字协同；但 **不能** 刷新页面才看到 AI 写完的 PRD

### B5. 信任与安全（产品经理能懂的）

- 标明 AI 只读了哪些代码仓、没改业务代码
- 密钥、MCP 设置产品经理看不见
- 失败用人话：Claude 没登录、代码仓路径没了、Git 冲突、权限不够

### B6. 以后再做（设计稿里标成「非本阶段」，但信息架构要留位）

- 拆 SR、测试方案与用例
- 让 AI **改业务代码**（单独开门）
- 安装包打磨、局域网邀请流的视觉
- 实时双人光标
- 文档仓以外的 Wiki/Notion 同步

## C. 给云端 Agent 的提示词（复制即用）

下面整段贴给云端 Cursor。**本阶段禁止写任何业务代码、禁止脚手架、禁止改 `apps/`。** 只产出产品设计文档。

```text
你是资深产品经理 + UX，不是工程师。本轮只做产品设计，禁止实现、禁止开 PR 改应用代码、禁止新增 npm 依赖。

## 产品一句话（锁死）

技术人员配好环境后，产品经理把「翻代码做调研、补 PRD」托付给 AI；人在墨览里改 Markdown。人写的和 AI 写的文档都用 Git 做版本。浏览器必须能及时看到磁盘/Git 上的文档变化。不是笔记库，不是 ChatGPT 壳，不是给工程师用的 IDE。

## 已拍板（设计不得违背）

- 安装程序 + 本机服务器；全员浏览器；同一套 UI，架构师/产品经理靠账号角色
- 每工程：1 个文档根（可写，且是 Git 仓）+ N 个代码根（只读）
- Agent = Claude Agent SDK；session 与 HTTP 连接分离；MCP 默认全开、仅架构师可关
- 墨览只编辑字符串；写回走服务端；不要浏览器本地另存为
- 不做 Tauri 工作台、不做改业务代码、不做公网 SaaS、不做实时双光标

## 你必须提前设计、不能留给开发猜的点

1. 文档 Git：何时 commit、AI 写入是否直接进历史、提交说明、对比/回退/恢复长什么样、多人冲突、要不要分支、要不要 remote
2. 文件变化如何到 Web：AI 写完、另一人保存、git pull 之后，墨览和文件树怎么更新；有未保存修改时怎么选
3. 产品经理主路径：从「打开已配好的工程」到「AI 调研代码并改出一版 PRD」到「人改并留下版本」——逐步界面
4. 架构师配环境的最短路径（含：文档目录如何变成 Git 仓、挂 remote）
5. 长任务：离开再回来、取消、进行中文档已部分落盘
6. 信任：如何让产品经理相信 AI 没改代码、只读了哪些仓

## 产出四稿（都要写进 doc/，用中文）

每稿结构：结论 → 理由 → 你自己挑 3 个漏洞 → 下一稿怎么补。不要四稿重复堆砌，要迭代。

- 第 1 稿 `doc/11-设计稿-1-问题与功能.md`
  用户故事、Jobs-to-be-done、功能优先级（P0 产品经理能托付调研并留下 Git 版本 / P1 / 以后）。不要技术组件清单。

- 第 2 稿 `doc/11-设计稿-2-信息架构与主路径.md`
  页面地图、架构师 vs 产品经理首屏、工作台三栏各自职责、共创/拷问/可行性怎么切换。关键路径用文字线框（ASCII 即可）。

- 第 3 稿 `doc/11-设计稿-3-Git与文档同步.md`
  专门把 B3+B4 做成可执行的交互说明：保存、commit、AI 采纳、冲突、file-changed、历史时间线。给出你推荐的默认策略（要拍板级，不要并列五个同等方案）。

- 第 4 稿 `doc/11-设计稿-4-综合与待拍板.md`
  合并前三稿成一份「当前推荐产品设计」；列出仍需人拍的问题（最多 8 个，带你的倾向）；更新 doc/02-UX讨论稿.md 的过时段落，使其与第 4 稿一致；在 doc/09 里加一句：产品设计以 doc/11-设计稿-4 为准，实现仍禁止到人说开始写代码为止。

## 质量

- 写产品经理能看懂的句子，少行话
- 每个交互写清：用户做什么、系统反馈什么、失败时说什么
- 不要写 API 路径当正文（第 3 稿可用附录）
- 不要发明已拍板相反的安装形态
- 四稿都写完后停，等人审。不要开始写 apps/ 里的代码
```
