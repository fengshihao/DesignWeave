# 多智能体：开源方案调研

> 状态：调研记录 · 2026-08-19 · **不实现，等人讨论**  
> 问题：需求分析、代码调研 / 架构方案、测试用例（人工 + 自动化）要不要拆成多个 Agent？有没有现成开源可借？  
> 配套：[00](./00-产品重定位.md)、[01](./01-Claude配置复用与工程绑定.md)、[08](./08-Agent对话UI选型.md)、[09](./09-云端迭代入口.md)、[11-设计稿-1](./11-设计稿-1-问题与功能.md)

本稿只回答三件事：① 开源世界实际有什么；② 和 DesignWeave 已拍板的栈合不合；③ 建议怎么拆、先不拆什么。不改 `apps/`。

---

## 结论

**可以拆，而且产品层已经拆过一半。** Schema 里早有 `designer` / `architect` / `qa` 三个角色，以及共创、拷问、可行性、拆 SR、测试方案等模式。工作台第一版只用了右侧三个档位（共创 / 拷问 / 可行性），并且是**同一个 Claude Agent SDK session 换提示词**，不是三个独立 Agent。

开源里**没有**一个现成产品等于「给产品经理的文档工作台 + 只读代码仓 + 本机 Claude + 多角色流水线」。有的是三类可借的东西：

| 层 | 是什么 | 代表 | 对我们 |
|----|--------|------|--------|
| **A. 方法包** | 角色提示词 + 阶段工作流 + Markdown 交接 | BMAD、GitHub Spec Kit、OpenSpec、Playwright Test Agents、Anthropic `feature-dev` | **最该偷。** 不换运行时 |
| **B. SDK 原生子能力** | 一个主 Agent 拉出隔离上下文的工人 | Claude Agent SDK **subagents**；实验性 **Agent Teams** | **阶段内部**可用，现在工作台没开 `Agent` 工具 |
| **C. 另起编排运行时** | Python/图/对话编排另一套引擎 | CrewAI、LangGraph、AutoGen/AG2、AgentScope、MetaGPT、ChatDev | **不采用。** 和 [09 §2](./09-云端迭代入口.md)「继续 Claude Agent SDK、不引入 Python 运行时」打架 |

推荐方向（供拍板，不是实现计划）：

1. **人看到的是角色 / 档位，不是进程。** 需求、调研方案、测试仍是三个交付阶段；人在阶段之间拍板。不要做成「一句话自动跑完 PM→架构→测试」。
2. **Agent 之间靠文档仓交接，不靠互相聊天。** `PRD.md` → `调研.md` / 技术方案 → 以后的 SR / 测试方案。这和 MetaGPT 的 SOP、BMAD 的 sharding 是同一条洞察，我们已经走在这条路上。
3. **真并行只放在阶段内部。** 例如可行性同时扫多个代码仓、架构同时出 2～3 套方案。用 SDK subagents，不要换 CrewAI。
4. **测试要拆两层。** 人工 / 验收用例写进文档仓（产品本分）；自动化脚本写进代码仓（当前默认禁止，须单独开门）。Playwright 官方 planner 的 Markdown 计划正好可当「人工用例」交付物。

## 1. 我们现在到底是不是「一个 Agent」

是。`apps/agent` 的工作台一次 `query()`，按档位换 `appendSystemPrompt`，工具是 Read/Write/Edit/Glob/Grep，**没有** `Agent` 工具，也没有 `agents:` 定义。

产品设计已经按角色想过：

```text
想法 / 口述 / 粘贴草稿
        ↓ 共创、细化、拷问          ← designer
      PRD.md
        ↓ 只读看代码仓
      可行性 + 技术方案              ← architect
        ↓ 拆任务
      SR / 任务清单
        ↓
      测试方案与用例                  ← qa
```

[11-1](./11-设计稿-1-问题与功能.md) 把「拆 SR、测试方案」标成**以后**；P0 只保证产品经理能托付一次可行性并留下 Git 版本。所以「多个 Agent」是信息架构留位，不是第一刀。

用户这次说的三块，和已有角色几乎一一对应：

| 用户说的 | 已有角色 / 模式 | 交付物（已有或留位） |
|----------|-----------------|----------------------|
| 分析需求 | designer：共创 / 细化 / 拷问 / 自洽 | `PRD.md`、`gaps.md` |
| 调研、架构、出方案 | architect：可行性 / 拆 SR | `调研.md`；以后技术方案、SR |
| 测试用例（自动 + 人工） | qa：测试方案 | 以后；人工用例进文档仓，自动化另说 |

差别只在：**现在是人换档位、同一套对话；用户在问要不要换成多个专职 Agent。**

## 2. 开源世界分三层（不要混着比）

「多智能体」这个词在外面至少指三种完全不同的东西。混在一起会以为必须上 CrewAI 才能有 PM / 架构师 / QA。

### 2.1 层 A：方法包（一个编码 Agent + 角色剧本）

人（或主 Agent）按阶段调用不同人格，产出 Markdown，下一阶段读上一阶段的文件。运行时仍是 Cursor / Claude Code / Copilot。

**BMAD-METHOD**（MIT，[bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)）  
角色最像我们：Analyst、PM、Architect、QA，外加 Scrum Master、UX 等。安装进 IDE，本质是 `.bmad-core` 里的 Markdown/YAML 人设 + 工作流。v6 有 Party Mode（同一会话里多个人格对谈）。**Test Architect (TEA)** 是独立模块：风险评分（概率 × 影响）、测试策略、ATDD、Playwright/Cypress 脚手架、需求追溯、发布门禁。这是目前最完整的「测试架构师」开源剧本。

合拍：角色切分、文档交接、人在过程里思考（BMAD 自称不替人想）。  
不合拍：面向**写代码的人**在 IDE 里用；流程偏重、默认会走到实现；不是给产品经理的浏览器工作台。可偷模板和阶段名，不要把 BMAD 装进产品当引擎。

**GitHub Spec Kit**（MIT，[github/spec-kit](https://github.com/github/spec-kit)）  
Spec → Plan → Tasks → Implement。斜杠命令驱动，agent-agnostic（Claude Code / Cursor / Copilot 等）。强调「规格是真相，代码服务规格」。

合拍：交付物进 Git、阶段门。  
不合拍：为**实现功能**服务；没有产品经理共创 / 拷问；测试不是一等公民。可偷「每阶段一篇 Markdown、下一阶段只读上一篇」。

**OpenSpec**（[Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)）  
每个变更一个目录：proposal / specs / design / tasks。后来补了把任务拆给多个 Agent 并行的 workflow。哲学更轻：随时改任一产物，不搞死板阶段门。

合拍：文档仓形状、跨仓规格（他们叫 Stores）。  
不合拍：给工程师改代码；多 Agent 编排绑 Claude Code Agent Teams（实验特性）。

**Anthropic `feature-dev` 插件**（[claude-plugins-official](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/feature-dev)）  
同一 SDK 上的官方范例。`/feature-dev` 七阶段：澄清 → **并行** `code-explorer` → 提问 → **并行** `code-architect`（最小改动 / 干净架构 / 折中，人来选）→ 实现 → **并行** `code-reviewer`。子 Agent 只读、有工具白名单。

合拍：**这就是我们应该抄的「阶段内并行」形状**，而且已经在 Claude Agent SDK 上。  
不合拍：为目标是写代码的人；没有 PRD 共创，没有给测试人员的人工用例。

**Playwright Test Agents**（官方，[playwright.dev/docs/test-agents](https://playwright.dev/docs/test-agents)）  
三个子 Agent：

- **planner**：探应用 + 可选 PRD → `specs/*.md`（步骤 + 期望，人能读）
- **generator**：Markdown 计划 → Playwright 测试文件（边点边核选择器）
- **healer**：失败则修定位器，修不好就 skip

`npx playwright init-agents` 会把定义写进 Claude Code / VS Code / Codex。社区仓库（如 playwright-testgen）多是这一套的包装。

合拍：人工用例（Markdown 计划）和自动化脚本天然分开；planner 的输出可以直接进我们的文档仓。  
不合拍：generator/healer 要写代码仓、要跑浏览器；产品经理工作台默认不改业务代码。

### 2.2 层 B：Claude Agent SDK 已经能「多个 Agent」

官方文档（2026）：[Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)。

主 Agent 通过 `Agent` 工具拉起子实例。每个子 Agent：**独立上下文**（中间 Grep/Read 不灌进主对话，只回摘要）、可并行、可限制工具、可换模型。定义方式：`query({ options: { agents: { ... } } })`，或 `.claude/agents/*.md`。SDK 应用官方推荐程序化定义。

和我们直接相关的能力：

- 可行性：一个 `code-researcher` 只读某个代码根，并行多个。
- 架构：2～3 个 `architect` 各出一套方案，主 Agent 汇总，**人来选**（feature-dev 就是这么干的）。
- 测试：`test-planner` 只许 Read/Grep/Write 文档仓；将来若开门，`test-generator` 才许碰测试目录。

另有实验性 **Agent Teams**（`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`）：多个完整 Claude Code 会话，共享任务列表、互相发消息。官方写明：恢复会话、任务协调、关闭行为有已知限制。适合「多人同时改一层代码」，**不适合**我们这种「人在墨览里定稿」的产品。第一版不要绑。

现状缺口：工作台 `allowedTools` 没有 `Agent`，也没有 `agents` 表。打开它是实现问题，不是产品重选型。

### 2.3 层 C：另起编排运行时（明确不采用）

| 方案 | 形态 | 为何不拿来当引擎 |
|------|------|------------------|
| **CrewAI** | 角色 crew，顺序 / 层级委派 | Python；任务输出接力，检查点弱；会变成第二套 Agent 产品 |
| **LangGraph** | 有状态图、人在环上、可回放 | 生产编排很强，但是另一套运行时；我们已有 session 流 |
| **AutoGen / AG2** | Agent 互相聊天达成共识 | 对话环适合辩论，不适合「文档仓是真相」 |
| **AgentScope** | 分布式、可观察 | [08](./08-Agent对话UI选型.md)、[09](./09-云端迭代入口.md) 已否：只借鉴 session 形状，不上 Python |
| **MetaGPT** | 虚拟软件公司 SOP：PM→架构→PM 拆任务→工程师→QA | 角色最像；目标是**一行需求自动出代码**；绿场、少人闸；和「人改 Markdown、默认不改业务代码」相反 |
| **ChatDev** | 角色扮演软件公司 | 研究原型，不是工作台 |

MetaGPT 仍值得单独记一笔：**它证明「结构化交付物交接」比 Agent 互聊更能压幻觉。** 我们用 Git 文档仓做这件事，比他们的 message pool 更适合产品经理。

## 3. 测试这一块：开源其实已经拆成两条线

用户要「自动化测试用例 + 手动人工测试用例」。开源里这两件事很少由同一个 Agent 一次做完，而且也不该。

```text
PRD / SR / 调研.md
        │
        ▼
  测试策略 + 风险（谁测、测多深）     ← BMAD TEA test-design
        │
        ├─► 人工 / 验收用例 Markdown     ← Playwright planner 的 specs/*.md
        │         给测试人员执行、给评审看
        │
        └─► 自动化（Playwright 等）      ← generator + healer
                  必须写代码仓、跑浏览器
```

| 产物 | 该不该进 DesignWeave 文档仓 | 开源可参照 |
|------|-----------------------------|------------|
| 测试策略、范围、风险、环境 | 要 | TEA `test-design`、我们已有 `test_plan` 提示词 |
| 人工用例（步骤 / 期望 / 正向异常边界） | 要 | Playwright planner；TEA 覆盖矩阵 |
| Gherkin `.feature` | 可选，仍是文档 | 若干 STLC MCP（质量参差，当参考即可） |
| Playwright / 接口自动化代码 | **默认不要** | 官方 generator；须「改业务代码」那扇门打开之后 |
| 失败自愈 | 不要进工作台主路径 | healer；那是测试仓自己的事 |

OEM 场景里还有大量**不可自动化**的：机型 / 区域 / 权限弹窗 / 系统能力。人工用例不是自动化的可怜替代，是主交付物。

## 4. 和已拍板约束对齐

| 已拍板 | 对「多 Agent」的含义 |
|--------|----------------------|
| Agent = 托管机 Claude Agent SDK | 子 Agent 用 SDK 的 `agents`，不要换 LangGraph/CrewAI |
| 默认只写文档根、只读代码根 | 调研 / 架构 / 人工测试可以多 Agent；**写自动化测试代码不行**，除非单独开门 |
| 同一时刻一个写者（人 XOR AI） | 并行子 Agent 可以**读**多个仓，但**写文档仓仍要串成一轮 run**，否则和编辑锁冲突 |
| 长任务挂 `session_id`，可离开再续 | 主 session 续；子 Agent 默认不单独给产品经理一条对话 |
| 对话是侧栏档位，不是三个产品 | UX 不要变成「三个 ChatGPT」；仍是右栏换角色，最多看到「正在让调研工人扫设置 App」 |
| 人不看仓库、不配模型 | 子 Agent 的工具白名单、模型别名是架构师配置，产品经理只看见角色名和交付物 |
| P0 不做拆 SR、测试方案 | 本稿的拆分是**以后**的信息架构，不膨胀第一刀 |

[08](./08-Agent对话UI选型.md) 已否 CopilotKit / AgentScope Web UI。多 Agent 若做出进度，仍走 AG-UI 事件：主 run 上多几条「子任务开始 / 摘要回来」，不要给每个工人一个聊天窗口。

## 5. 三种产品形态（建议选 2，内部用 2b）

**形态 1 — 换提示词（现状）**  
一个会话、三个档位。实现最便宜，P0 够用。代价：可行性长调研会撑爆上下文；架构和需求人格混在同一段历史里。

**形态 2 — 阶段 = 专职 session，文档交接（推荐给人看）**  
产品经理仍觉得是「换角色」：

```text
共创/拷问  ──写──► PRD.md / gaps.md
                      │ 人改、定一版
可行性/方案 ──读上一版、只读代码──► 调研.md / 技术方案.md
                      │ 人改、定一版
测试        ──读 PRD+调研──► 测试方案.md / 用例.md
```

每个阶段可以是新的 SDK session（干净人格 + 只带上该读的文件），不必三个常驻进程互聊。人是阶段门。这就是 BMAD / Spec Kit / MetaGPT SOP 里真正可迁移的部分。

**形态 2b — 阶段内再开 subagent（推荐给机器用）**  
主 Agent 仍对用户说话；工人只干活、回摘要。典型：

- 可行性：每仓一个只读 researcher
- 架构：2～3 个方案工人，主 Agent 对比后**问人选哪套**（抄 feature-dev）
- 测试：planner 写 Markdown；不自动 generator

**形态 3 — 虚拟团队自动流水线（不建议）**  
MetaGPT / CrewAI 式一键 PM→架构→开发→QA。和「人负责判断、改文档、定稿」相反，也和人 XOR AI 的编辑锁难兼容。Agent Teams 实验特性也不要当产品承诺。

## 6. 建议从开源偷什么、不偷什么

**偷（思想 / 模板 / 形状）**

- BMAD：角色职责边界、阶段检查清单、TEA 的风险优先级（P0–P3）和「人工 vs 自动化」分层  
- Spec Kit / OpenSpec：一阶段一 Markdown、Git 为真相、下一阶段只读上一篇  
- feature-dev：只读 explorer、多方案 architect **让人挑**、子 Agent 工具白名单  
- Playwright planner：人工用例的 Markdown 形状（场景 / 步骤 / 期望），可直接当文档仓模板  

**不偷（当引擎、当壳、当自动写代码）**

- CrewAI / LangGraph / AutoGen / AgentScope 进程  
- MetaGPT 自动出代码的公司模拟  
- Playwright generator/healer 默默写进业务仓  
- 把 BMAD / Spec Kit 安装进托管机当用户可见产品（产品经理会掉进 IDE 工作流）

**以后若做测试档位，优先顺序**

1. 文档仓里的策略 + 人工用例（对齐 qa 角色、不改代码）  
2. 可选：把 Playwright planner 当 **技能 / 子 Agent 定义** 复用，输出仍只写文档仓  
3. 自动化生成：等「改代码」开门，且测试目录策略拍板后再说

## 7. 待讨论（建议人拍）

最多六问，带倾向：

1. **人看到几个 AI？** 倾向：还是右栏一个对话，换「需求 / 调研方案 / 测试」角色；不要三个并列聊天。  
2. **阶段之间自动往下跑吗？** 倾向：**不自动。** PRD 没人定稿，不开可行性；调研没人定稿，不开测试。  
3. **P0 要不要开 subagent？** 倾向：**不要。** 先把单 session 三档位做稳。可行性上下文不够再开只读 researcher。  
4. **测试档位何时进信息架构？** 倾向：顶栏留位可以现在就画；实现仍「以后」。人工用例模板可先写进文档规范，不必等 Agent。  
5. **架构师出方案时要不要「同时三套、人选一套」？** 倾向：要，这是 feature-dev 里最值的一刀；放在调研方案阶段，不放 P0。  
6. **自动化用例算不算「改业务代码」？** 倾向：算，除非架构师单独挂「可写的测试根」。第一版只出人工用例 Markdown。

## 8. 和第一刀的关系

本稿**不改变** [09 §3](./09-云端迭代入口.md) / [12](./12-实现前决策.md) 的 P0。不改 `apps/`。

若拍板接受「形态 2 + 以后 2b」：

- 设计稿以后改信息架构时：右栏档位从三个变成「按角色」，测试从隐藏变成留位  
- `packages/prompts` 里已有的角色提示词可以当后一阶段的草稿，不必另起框架  
- 实现第一刀仍然是：一个 Claude session、三档、只写文档仓  

讨论清楚之前，不要引入 BMAD 安装器、不要开 Agent Teams、不要加 LangGraph。
