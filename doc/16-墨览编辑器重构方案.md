# 墨览编辑器重构方案

> 状态：待评审 · 2026-08-20
> 目的：把墨览编辑器从"4346 行 IIFE 单文件 + 拷贝式分发"重构成"可被 VS Code / Web / 浏览器工作室三端复用的模块化内核"。本文是 `doc/15-项目整体Review.md` 第 2.2 / 阶段 5 的展开。
> 范围：只谈编辑器内核与三端集成，不谈工作台后端。

---

## 0. 一句话结论

把 `tools/markdown-viewer` 里那套 IIFE + 拷贝的编辑器，重构成一个 **ESM npm 包 `@designweave/molan-core`**，三端用 `import` 而非拷贝；同时把宿主↔编辑器的 `postMessage` 协议抽成 **共享类型包 `@designweave/molan-protocol`**，把三端重复的桥接逻辑抽成 **`@designweave/molan-host`**。分四步走，每步可独立交付、可独立回滚，不追求一步到位。

---

## 1. 现状（重构的起点）

### 1.1 真源与分发

- `tools/markdown-viewer/` 是唯一真源
  - `molan-editor.js` 4346 行 / 153KB，编辑器内核（IIFE 挂 `window.MolanEditor`）
  - `molan.css` 3912 行 / 107KB，全部样式（四主题 + Vditor 覆盖 + 工作室 UI）
  - `molan-app.js` 1725 行 / 55KB，浏览器工作室独有（选文件夹/侧栏/IndexedDB）
  - `molan-i18n.js` 1841 行 / 85KB，11 语言字符串
  - `molan-aphorisms.js` 1008 行 / 72KB，欢迎页格言
  - `vendor/vditor/` gitignore，Vditor 裁剪版（由 sync 脚本生成）
  - `index.html` 浏览器工作室入口
  - `guide.html` / `extension.html` 营销页（不加载编辑器 JS）
- 两个 sync 脚本直拷贝：
  - `apps/vscode-molan/scripts/sync-media.mjs` → `apps/vscode-molan/media/`
  - `apps/web/scripts/sync-molan.mjs` → `apps/web/public/molan/`
- 产物在 `.gitignore` 里（`.gitignore:21-26`）

### 1.2 三端宿主

| 端 | 宿主 HTML | 桥接 JS | 通道 | 产物位置 |
|----|-----------|---------|------|----------|
| 浏览器工作室 | `tools/markdown-viewer/index.html` | `molan-app.js` | 同进程直接调 `window.MolanEditor` | 真源即产物 |
| VS Code 扩展 | `markdownEditorProvider.ts` 内联 `getHtml()` | `media/vscode-bridge.js` | `vscode.postMessage` ↔ `webview.onDidReceiveMessage` | `apps/vscode-molan/media/` |
| Web 工作台 | `apps/web/public/molan/host.html` | `public/molan/web-bridge.js` | `window.parent.postMessage` ↔ iframe `onMessage` | `apps/web/public/molan/` |

### 1.3 对外 API 契约（从 bridge 反推，目前无类型定义）

- 工厂：`window.MolanEditor.create({ elementId, cdn, linkBase, previewActions, onInput, onCounter, onSave }) -> Promise<EditorApi>`
- 实例：`api.getValue() / setValue(value, clearStack?) / setPreview(bool) / isPreview() / focus() / onPreviewChange(cb)`
- 静态：`MolanEditor.toast(msg) / countWords(text) / find.open/next/prev()`

### 1.4 已经暴露的痛点（证据）

1. **两个 bridge 90% 重复**：`web-bridge.js`（211 行）和 `vscode-bridge.js`（233 行）的 `setChrome / syncModeButton / scheduleEditorIdleWork / ensureEditor / applyHostContent` 几乎逐行相同，只差 `post()` 实现（`window.parent` vs `vscode`）和几端独有功能（web 有 readOnly/wantEdit/getState/exitEdit；vscode 有 find/openRelative）。
2. **宿主 HTML 模板重复**：`markdownEditorProvider.getHtml()`（281–411 行）和 `host.html` 各内联一整套 `reader-header / lightbox / toast` DOM，改一个图标要改两处。
3. **拷贝已经漂移**：本次 review 时 `apps/web/public/molan/molan-editor.js` 是 77KB（8 月 16 日），而真源是 153KB（8 月 20 日），`apps/vscode-molan/media/molan-editor.js` 是 150KB（8 月 20 日）。web 产物过期 4 天没人发现——正是拷贝式分发的典型症状。
4. **vendor 子集不一致**：web 只拷 `js/i18n/zh_CN.js`，vscode 拷整个 `js/i18n`。同一份编辑器在 web 和 vscode 的语言回退行为可能不同。
5. **无类型契约**：`MolanFrame.tsx` 和两个 bridge 之间是 `postMessage` 字符串协议，重命名一个消息类型要靠 grep 三处。
6. **单文件不可分**：`molan-editor.js` 4346 行，`create` 工厂 423 行，`bindBlockInsert` 328 行，模块级 `let` 共享状态（`toastEl`/`findState`/`mermaidRenderSeq`）。
7. **CSS 单文件 3912 行**：四主题重复块、Vditor `!important` 覆盖、工作室 UI 混在一起。

## 2. 目标架构

### 2.1 三个新包

- `packages/molan-protocol/` 纯类型 + 消息校验（无运行时依赖）
- `packages/molan-core/` 编辑器内核 ESM（从 tools/markdown-viewer 迁来）
- `packages/molan-host/` 三端宿主公共逻辑（bridge + HTML 模板）

三者关系：

```
        molan-protocol（类型契约，三端共享）
              ▲
              │ import type
   ┌──────────┼──────────┐
   │          │          │
molan-core    molan-host   宿主侧 React/VSCode 组件
(编辑器内核)  (bridge+HTML) (MolanFrame / EditorProvider)
```

### 2.2 各端怎么用

| 端 | 用什么 | 怎么集成 |
|----|--------|----------|
| 浏览器工作室 | `molan-core` + `molan-host/standalone` | Vite 打包成 `index.html` 单页，`molan-app.js` 只剩工作室壳（选文件夹/侧栏） |
| VS Code 扩展 | `molan-core` + `molan-host/vscode` | `markdownEditorProvider.ts` 调 `molan-host/vscode` 生成 webview HTML + bridge，bridge 用 `vscode.postMessage` |
| Web 工作台 | `molan-core` + `molan-host/iframe` | `MolanFrame.tsx` 用 `molan-host/iframe` 的 React hook 包 iframe，bridge 用 `window.parent.postMessage` |

### 2.3 关键决策

**D1. 编辑器内核仍然是"挂 window"还是改 ESM？**
答：改 ESM。`molan-core` 导出 `createEditor(options): Promise<EditorApi>`，不再挂 `window`。三端 `import`。浏览器工作室和 vscode webview 都支持 ESM（vscode webview 支持 `<script type="module"`，需在 CSP 里放行）。

**D2. Vditor 怎么加载？**
答：保持"预览用 `method.min.js`，点编辑再懒加载 `index.min.js`"的双段策略，但加载方式从"动态 `<script>` 注入 + CDN 路径"改成"由 `molan-core` 内部用 `import()` 动态导入 vendored 模块"。vendor 作为 `molan-core` 的 `dependencies`（或 `peerDependencies`），由各端 bundler 处理产物路径，不再靠 sync 脚本拷贝。

**D3. iframe 还要不要？**
答：Web 工作台继续用 iframe（隔离 Vditor 的全局 CSS / 主题，避免污染工作台 UI）。VS Code 用 webview（本来就是隔离的）。浏览器工作室不需要隔离，直接挂 DOM。所以 `molan-host` 提供两种集成模式：`inline`（直接挂 DOM）和 `framed`（iframe/webview）。

**D4. CSP 怎么处理？**
答：VS Code webview 的 CSP 最严（`script-src 'nonce-xxx'`），`molan-host/vscode` 负责生成带 nonce 的 HTML 和 script 标签。Web iframe 用同源，CSP 由外层 Next.js 控制。`molan-core` 内部不假设 CSP，所有脚本加载走参数化路径。

**D5. 主题与 CSS？**
答：`molan-core` 导出一个 `molan.css`（只含编辑器自身样式 + 主题变量），不再含工作室 UI。工作室 UI 样式留在 `molan-app`。三端 `import 'molan-core/style.css'`（或由 bundler 处理）。四主题用 `:root` + `[data-theme]` 覆盖，消除重复块。

## 3. 分步方案

每步**独立可交付、独立可回滚**。不追求一步到位，每步完都能跑通三端。

### 步骤 1：抽 `@designweave/molan-protocol`（类型契约，1 天，风险极低）

**做什么**
- 新建 `packages/molan-protocol/src/`，用 TS 定义：
  - `EditorOptions`（create 的入参）
  - `EditorApi`（实例方法签名）
  - `HostToFrameMessage` / `FrameToHostMessage`（postMessage 联合类型，含 `init/setContent/setReadOnly/saved/getState/exitEdit` 和 `ready/save/change/previewChange/wantEdit/theme/state`）
  - `MolanState`（value/dirty/isPreview）
- 导出 zod schema 做运行时校验（可选，先只出类型）。
- `packages/molan-protocol/package.json`：`"type": "module"`，tsc 出 `.d.ts`，无运行时代码。

**怎么接入**
- `apps/web/src/components/MolanFrame.tsx` 的 `HostToFrame` / 消息处理改用 `import type { HostToFrameMessage, FrameToHostMessage } from "@designweave/molan-protocol"`。
- `apps/vscode-molan/src/markdownEditorProvider.ts` 的 `msg: { type?: string; ... }` 改用同一类型。
- 两个 bridge 暂时**不动**（还是 IIFE），但加一行注释指向 protocol 包，作为后续替换的锚。

**收益**：三端消息类型有了单一来源，重命名一个消息类型改一处即可，typecheck 能跨三端报错。

**回滚**：删掉包，恢复手写类型。零风险。

---

### 步骤 2：抽 `@designweave/molan-host`（桥接层，2～3 天，风险低）

**做什么**
- 新建 `packages/molan-host/src/`，把两个 bridge 的重复逻辑抽成公共核心 + 三端适配器：
  - `core.ts`：`createBridge({ post, onMessage })` 返回 `{ setChrome, syncModeButton, ensureEditor, applyHostContent, applyReadOnly, ... }`，纯逻辑，不碰 DOM 通道。
  - `vscode.ts`：`createVscodeBridge()` 用 `acquireVsCodeApi()` 做 post/onMessage，包 `core`，加 find/openRelative。
  - `iframe.ts`：`createIframeBridge()` 用 `window.parent` 做 post/onMessage，包 `core`，加 readOnly/wantEdit/getState/exitEdit。
  - `html.ts`：`renderHostHtml({ vditorCdn, linkBase, nonce?, bridgeSrc, theme })` 生成宿主 HTML（reader-header/lightbox/toast DOM），消除 `getHtml()` 和 `host.html` 的重复。
- `molan-host` 依赖 `molan-protocol` 的类型。

**怎么接入**
- `apps/vscode-molan/media/vscode-bridge.js` 改成由 `molan-host/vscode` 打包产物替代（vscode 扩展 build 时 bundle 进 media）。
- `apps/web/public/molan/web-bridge.js` 同理。
- `markdownEditorProvider.getHtml()` 改调 `renderHostHtml(...)`。
- `host.html` 改成由 `renderHostHtml(...)` 在 web build 时生成（或 Next.js route 动态返回）。

**收益**：bridge 重复消除，HTML 模板单一来源。改一个图标改一处。

**回滚**：恢复两个 bridge + 两份 HTML。风险低，因为 `core.ts` 是纯逻辑可单测。

---

### 步骤 3：把 `molan-editor.js` 改成 `@designweave/molan-core`（内核 ESM 化，3～5 天，风险中）

这是最大的一步，建议再拆成 3 个子步。

**3a. 包骨架 + 整体迁入（1 天）**
- 新建 `packages/molan-core/`，`package.json` 声明 `"type": "module"`、`exports`（`./editor`、`./style.css`）、`dependencies: { vditor }`。
- 把 `tools/markdown-viewer/molan-editor.js` 原样移进 `packages/molan-core/src/legacy.js`，用一个 thin wrapper 重新挂 `window.MolanEditor`（**临时**，保兼容）。
- 三端 sync 脚本改成从 `packages/molan-core/dist/` 拷贝（而不是 `tools/markdown-viewer/`）。此时三端行为不变，但真源已经是 npm 包产物。

**3b. 拆模块（2～3 天）**
按区段把 `legacy.js` 拆成 ES modules，每个 < 500 行：

- `packages/molan-core/src/`
  - `index.ts` 导出 `createEditor / toast / countWords / find`
  - `editor.ts` `create()` 工厂（原 3925–4347）
  - `vditor-loader.ts` `loadScript / ensureFullVditor / preloadLute`（原 6–66）
  - `i18n.ts` 内联回退字典（原 76–171），与 `molan-i18n.js` 合并去重
  - `mermaid.ts` 主题/渲染/预览增强（原 172–407, 648–822）
  - `lightbox.ts` 流程图灯箱（原 408–647）
  - `table.ts` 表格布局/工具条/picker（原 823–1332）
  - `outline.ts` 大纲（原 1350–1555）
  - `chrome.ts` 顶栏 UI 注入（原 1556–1686）
  - `format-bar.ts` 选区格式（原 1716–1961）
  - `find.ts` 查找 + CSS Highlight API（原 2158–2869）
  - `typography.ts` 字号/主题切换（原 2870–3178）
  - `block-insert.ts` 行首"+"插入（原 3179–3924）

模块级 `let`（`toastEl`/`findState`/`mermaidRenderSeq`）收进 `editor.ts` 的工厂闭包，或抽成 `EditorState` 类。每个模块导出纯函数，由 `editor.ts` 组装。

**3c. 切断 window 挂载（0.5 天）**
- `index.ts` 只导出 `createEditor`，不再挂 `window.MolanEditor`。
- 三端 bridge 改成 `import { createEditor } from "@designweave/molan-core"`（此时 bridge 已是 `molan-host` 产物，步骤 2 已完成）。
- 删除 `tools/markdown-viewer/molan-editor.js` 和两个 sync 脚本对它的拷贝。

**风险与缓解**
- 拆模块时最容易出回归的是"模块级 `let` 被多个函数共享"——拆的时候要先把状态显式传参或收进闭包，再动函数边界。
- 每拆一个模块跑一遍 `table-e2e.mjs` + 手动点一遍预览/编辑/查找/主题/表格/行首+。
- 建议在 3b 之前先补 2～3 条 Playwright（预览/编辑切换、查找、主题切换）作为回归网。

**回滚**
- 3a 可回滚（恢复 `tools/markdown-viewer/molan-editor.js` 为真源）。
- 3b 一旦开始拆，回滚成本上升；建议按模块逐个拆、逐个合，每个模块独立 commit，出问题可单模块 revert。
- 3c 是不可逆点（删 window 挂载），务必在三端都切到 `import` 后再删。

### 步骤 4：拆 `molan.css` + 工作室壳化（1～2 天，风险低）

**做什么**
- 把 `tools/markdown-viewer/molan.css` 拆成：
  - `packages/molan-core/src/style.css`：编辑器自身样式（Vditor 覆盖、reader-header、lightbox、format-bar、find 高亮、typography 变量）。四主题用 `:root` + `[data-theme=night/hack/rose]` 覆盖，**消除重复块**（用 CSS 变量统一，主题只覆盖变量值）。
  - `tools/markdown-viewer/studio.css`：工作室 UI（sidebar/welcome/statusbar），只 `molan-app` 用。
- `molan-core` 的 `package.json` 导出 `"./style.css"`，三端 `import "@designweave/molan-core/style.css"`（由 bundler 处理）。
- `tools/markdown-viewer/molan-app.js` 瘦身：只保留工作室壳（选文件夹/侧栏/IndexedDB/格言），编辑器部分全部 `import` 自 `molan-core`。`molan-i18n.js` / `molan-aphorisms.js` 可考虑也收进 `molan-core`（作为可选导出），或留在工作室壳。

**收益**：CSS 单一来源、主题变量化、工作室与编辑器解耦。

**回滚**：恢复单文件 `molan.css`。

## 4. vendor（Vditor）管理与构建

当前 vendor 由两个 sync 脚本各自裁剪拷贝，子集不一致。重构后统一：

1. `packages/molan-core/package.json` 把 `vditor` 列为 `dependencies`（或 `peerDependencies`，让三端各自装）。
2. `molan-core` 内部用 `import()` 动态加载 Vditor 的 `method.min.js`（预览）和 `index.min.js`（编辑），路径由 bundler 解析。不再有"CDN 字符串"。
3. 各端 bundler 负责 tree-shake / 裁剪：
   - VS Code 扩展：esbuild/webpack bundle 进 `media/`，保留全量 i18n。
   - Web 工作台：Next.js 处理，按需只留 `zh_CN`。
   - 浏览器工作室：Vite 打包。
4. 删除 `sync-media.mjs` / `sync-molan.mjs` 里对 `molan-editor.js` / `molan.css` / `vendor/vditor` 的拷贝逻辑（这些由 bundler 接管）。脚本若还需拷贝其他静态资源（图标等），保留那部分。

**注意**：Vditor 的 `method.min.js` / `index.min.js` 是 UMD，不是 ESM。`import()` 加载 UMD 需要 bundler 配合（esbuild 的 `loader: 'js'` + `format: 'iife'`，或用 `<script>` 注入兜底）。这一块要在步骤 3a 验证可行后再推进，是 D2 的主要技术风险点。

## 6. 迁移路径与兼容期

不要求三端同时切换。建议顺序：

1. **步骤 1（protocol）**：三端同时接入类型，无运行时变化。
2. **步骤 2（host）**：先 web 工作台切到 `molan-host/iframe`，跑稳一周；再 vscode 切到 `molan-host/vscode`。两端切换期间，旧 bridge 保留在仓库里（标 deprecated），新 bridge 并行存在，出问题可切回。
3. **步骤 3（core ESM）**：3a 包骨架后，三端 sync 脚本改从 `molan-core/dist` 拷贝（行为不变）。3b 拆模块逐个合。3c 切 import 时，三端 bridge 已是 `molan-host` 产物，只需改 `molan-host` 内部 import 来源，三端宿主代码不用动。
4. **步骤 4（CSS）**：最后做，与 core 解耦后风险最低。

**兼容期原则**：任何一步都允许"新包产物 + 旧直拷贝"并存一段时间，由 sync 脚本/ bundler 决定用哪个。只有 3c（删 window 挂载）是不可逆点。

## 7. 风险与回滚总表

| 步骤 | 风险 | 主要风险点 | 回滚成本 |
|------|------|-----------|----------|
| 1 protocol | 极低 | 无运行时 | 删包 |
| 2 host | 低 | bridge 行为差异（find/openRelative 只在 vscode，readOnly/getState 只在 web） | 恢复两份 bridge + HTML |
| 3a core 骨架 | 低 | sync 脚本路径改 | 改回路径 |
| 3b 拆模块 | 中 | 模块级 `let` 状态共享、Vditor UMD 加载 | 逐模块 revert |
| 3c 切 import | 中高 | 三端 bundler 对 Vditor UMD 的处理、CSP nonce | 临时恢复 window 挂载 |
| 4 CSS | 低 | 主题变量化遗漏 | 恢复单文件 css |

**最大技术风险**：D2（Vditor UMD 改 import）。若 3a 验证发现 bundler 无法干净加载 Vditor UMD，可回退方案：保留"动态 `<script>` 注入"，但把注入路径参数化进 `molan-core`，由包统一管理，三端不再各自 sync vendor。这样仍能消除拷贝漂移，只是没完全 ESM 化。

## 8. 给评审 AI 的提问清单

1. **是否值得做成 npm 包，而不是只抽类型 + 保留拷贝？** 拷贝式分发虽然丑，但三端改动频率是否高到值得花 3～5 天做 ESM 化？中间方案（只做步骤 1+2，core 仍拷贝）是否性价比更高？
2. **Vditor UMD 改 import 的可行性**：有没有人在 Next.js / vscode webview / Vite 三种环境里成功 `import()` 过 Vditor 的 `method.min.js` / `index.min.js`？若不可行，D2 的回退方案是否可接受？
3. **iframe vs inline 的取舍**：Web 工作台继续用 iframe 隔离 Vditor CSS 是否必要？还是可以靠 CSS scope / shadow DOM 去掉 iframe，减少一层 postMessage？
4. **`molan-host` 是否过度抽象？** 两个 bridge 重复 90%，但各自独有功能（find/openRelative vs readOnly/getState/exitEdit）也不少。抽 `core.ts` + 适配器是否真的比两份独立 bridge 更好维护？
5. **CSS 主题变量化能否彻底消除重复？** 四主题下查找高亮、欢迎页等重复块，靠 CSS 变量能否真的只剩 `:root` + 4 个 `[data-theme]` 覆盖？还是会有必须重复的边缘样式？
6. **步骤 3b 拆模块的边界是否合理？** 13 个模块的划分（mermaid/lightbox/table/outline/chrome/format-bar/find/typography/block-insert/...）是否太细或太粗？有没有更自然的边界（按 Vditor 生命周期 vs 按功能）？
7. **i18n / aphorisms 该进 core 还是留工作室？** 它们体积大（85KB / 72KB），vscode 扩展用不用格言？若只用 i18n，aphorisms 留工作室壳更合适。
8. **测试网够不够？** 提议的 3～4 条 Playwright + core 纯逻辑单测，能否覆盖拆模块的主要回归？有没有遗漏的高风险路径（如 Mermaid 渲染、流程图灯箱、行首"+"插入）？
